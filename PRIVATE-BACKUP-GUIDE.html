Database और media का encrypted backup

इसकी code व्यवस्था तैयार है। वास्तविक backup तभी चालू होगा जब owner नीचे की सुरक्षित settings पूरी करे और पहला run सफल हो। Source-code backup इससे अलग है।

Owner की एक बार की setup

  1. GitHub → Settings → Secrets and variables → Actions खोलें। केवल इसी Studio repository में setup करें।
  2. Repository secret STUDIO_BACKUP_DATABASE_URL: Studio Supabase के Connect → Session pooler से connection URI लें, port 5432 रखें और सही database password भरें। Password में विशेष चिन्ह URI-encode करें। Transaction pooler port 6543 न लें।
  3. Repository secret STUDIO_BACKUP_SERVICE_KEY: Studio की server-only legacy service_role key रखें। Publishable/anon key पर्याप्त नहीं है। यह key frontend, source code, email या chat में न डालें।
  4. Repository secret STUDIO_BACKUP_PASSWORD: password manager से नया random password बनाएँ, कम से कम 24 characters। यह database/login password से अलग हो। इसकी recovery copy अलग सुरक्षित रखें; इसके बिना archive नहीं खुलेगा। Password बदलें तो पुराने backup के लिए पुराना password भी चाहिए।
  5. Variables tab → New repository variable: STUDIO_PRIVATE_BACKUP_ENABLED = true। पहले secrets पूरे भरें, फिर enable करें।
  6. Encrypted backup workflow → Run workflow → main चुनें। दोनों jobs हरी होने चाहिए; केवल validation हरी और backup skipped होने का मतलब वास्तविक backup बंद है।

इसके बाद रोज़ लगभग 02:30 IST पर run निर्धारित है। GitHub scheduler में देरी हो सकती है। Owner को workflow-failure notifications चालू रखनी चाहिए। यह नया Supabase paid plan नहीं खरीदता; downloads पर provider egress और Actions/storage quotas लागू हो सकते हैं। वर्तमान safety limit 5,000 media objects / कुल 1 GiB media है; सीमा पार होने पर पूरा run fail होगा।

क्या सुरक्षित होगा

Database का PostgreSQL logical snapshot, Storage buckets का विवरण और API से downloaded media, checksum manifest—सब एक GPG AES256 encrypted archive में। Artifact में केवल encrypted file और उसका checksum जाएगा। Plaintext temporary files runner से हटेंगे। Artifact retention 30 दिन है; जरूरी encrypted copies अपनी अलग सुरक्षित जगह भी डाउनलोड करें।

Provider API secrets, custom database role passwords, Android signing keys और केवल फोन/browser में saved drafts इसमें नहीं आते। Studio के पूरा Backup से device drafts अलग रखें। Database और media एक atomic cross-service snapshot नहीं हैं। Quiet period में backup लें; inventory में बदलाव दिखे तो run fail होगा। पहले सफल artifact बनना, उसके बाद decrypt/checksum और अलग recovery environment में restore होना जरूरी है।

Download और सुरक्षित verification

  1. Successful workflow → Artifacts से APANAMai-private-encrypted-… डाउनलोड करें और ZIP खोलें।
  2. अपने सुरक्षित computer पर GnuPG और PostgreSQL 17 tools रखें। नीचे commands archive वाले folder में चलें। GPG password interactive prompt में भरें, command या history में नहीं।
sha256sum -c SHA256SUMS
gpg --output recovery.tar --decrypt APANAMai-private-backup.tar.gpg
tar -tf recovery.tar

GPG decrypt की exit status सफल होने पर ही archive उपयोग करें। Failed decrypt से निकला partial output हटाएँ। Manifest के database और हर media file के SHA256 जाँचें। Linux/macOS/WSL commands ऊपर हैं; Windows में PowerShell Get-FileHash से SHA256 और GnuPG से decrypt कर सकते हैं। खुले backup में private user/account data होगा; इसे public GitHub या shared public folder में upload न करें।

Recovery — live data पर अपने-आप restore नहीं होगा

पहले अलग, compatible Supabase/PostgreSQL recovery environment में restore करें। Managed auth/storage schemas, extensions, role names/grants और RLS की compatibility आवश्यक है; plain PostgreSQL test production Supabase restore का प्रमाण नहीं है। Custom roles/password और provider configuration अलग वापस setup करनी होगी। PostgreSQL 17 pg_restore --list database.dump से archive जाँचें; recovery environment में controlled restore करें। Live में restore से पहले नए payments, mandates और uploads reconcile करें—पुराना snapshot डालने से हाल का data छूट सकता है।

Media manifest में bucket/name → media/N.bin mapping, metadata, bytes और SHA256 है। Original buckets/policies सही करके Storage API से उन्हीं bucket/object names पर upload करना होगा। Database restore अकेले Storage files नहीं लौटाता। Access policies, login, project save/load, media/audio और payment records recovery environment में जाँचें, फिर planned production recovery करें।

Run fail हो तो

Missing secret/disabled variable → GitHub settings; connection failure → सही Studio host, session pooler, encoded password; Storage authorization → server service_role key; storage changed → quiet period में दुबारा run; quota/limit → private destination और backup capacity योजना बढ़ाएँ। Raw error में secrets या object names आ सकते हैं इसलिए script generic failure दिखाता है। Fail होने पर पहले वाला successful backup रखें और नए backup को पूरा न मानें।
