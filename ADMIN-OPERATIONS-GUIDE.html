रोज़ का काम

  1. Admin में अपने verified owner account से Login करें। सामान्य user को server admin अधिकार नहीं मिलते।
  2. संचालन / Recovery → स्थिति Refresh से catalog version और renewal records देखें। API Health → अभी जाँचें से configured services और दर्ज errors देखें।
  3. App Settings: नाम, मुख्य रंग, सूचना, support संपर्क, poster/video/user-upload switches। ये interface switches हैं; server payment/provider gates अलग हैं।
  4. Posters / Templates: editable JSON/photo जोड़ें, अवसर और तारीख भरें, नाम/category बदलें। Editor में बदलें से design बदलकर वापस admin draft सेव करें।
  5. Users / Profiles: खोज/filter करें; Detail से validity और संपर्क देखें। मुफ्त manual membership देना paid AI credits या admin अधिकार देना नहीं है।
  6. Business / Reminders: provider लागत और margin, email consent/limit/queue देखें। Email enable करने से पहले verified sender/API और scheduler स्थिति जाँचें।
  7. Publish से पहले संचालन Backup लें → Cloud draft Save → preview/spelling देखें → Cloud Publish → app refresh करके जाँचें।

₹10 registration → 15 दिन → ₹100 हर 30 दिन की नीति बनी रहती है। AutoPay के लिए merchant activation और user की explicit mandate consent दोनों जरूरी हैं।

API key / Email / Plan renewal

संचालन → Renewal में प्रत्येक service का provider account email और provider से मिली expiry/renewal date भरें। सात दिन बाकी/overdue संकेत दिखेंगे। Renewal Calendar से .ics file डाउनलोड करें और अपने calendar में import करें; उसमें 7, 3 और 1 दिन पहले के reminders हैं। Notifications calendar settings/समर्थन पर निर्भर हैं। यह page-open record tracking है; बाहर से स्वतः expiry/quota नहीं खींचता और स्वतः billing/renewal नहीं करता। खाली तारीख का मतलब “अज्ञात/लागू नहीं”, unlimited नहीं।

  1. Provider dashboard में credits/plan/key की असली स्थिति देखें। नया key बनाते समय पुराने integration का ध्यान रखें।
  2. Supabase → Edge Functions → Secrets में सही variable की नई value Save करें। Keys admin record, public GitHub, catalog JSON या chat में न डालें। Cloudflare Worker secrets उसके dashboard में बदलें।
  3. API Health Refresh करें। Configured केवल key की मौजूदगी बताता है; वास्तविक provider response/credit स्थिति के लिए logs या लागत समझकर provider test करें।
  4. सफल होने के बाद Renewal record की तारीख/स्थिति अपडेट करें। पुरानी key तभी revoke करें जब नई काम करे।

हर API key की निश्चित expiry नहीं होती। Provider credits, plan renewal और sender verification अलग-अलग बातें हैं।

Backup और खराब बदलाव वापस करना

संचालन Backup में current Draft/Published catalog और renewal metadata आता है। User media, database, payment balances, credentials और source code अलग हैं। Backup में source/secret शामिल होने का अनुमान न लगाएँ।

  1. Catalog/settings बिगड़े: Recovery सूची में पुराना version → JSON डाउनलोड → Draft में वापस खोलें। इससे live catalog तुरन्त नहीं बदलता। Templates preview देखें → Cloud Publish करें।
  2. प्रत्येक बदलने वाले Draft/Published catalog की पिछली पाँच अलग versions server पर सुरक्षित हैं। अधिक पुराने catalog के लिए अपनी डाउनलोड की गई JSON रखें।
  3. Backup import: संचालन JSON चुनें; Draft या Published catalog चुनें। केवल local draft खुलेगा। Renewal metadata अपने-आप overwrite नहीं होगा।
  4. Software/code बिगड़े: GitHub Actions में error देखें; पिछले सफल commit की बदली files वापस करके नया commit करें। Tests और Pages deployment सफल होने दें। source ZIP नियमित रखें।
  5. Database बिगड़े: Supabase backup/PITR उपलब्धता और तारीख जाँचें; पहले वर्तमान database export/backup लें। Catalog restore user payments/memberships को वापस नहीं करता। Live database restore के लिए सावधानी और database विशेषज्ञ की जरूरत हो सकती है।
  6. Users के photo/audio/video का local पूरा backup भी रखें। Android/desktop browser data साफ करने से local projects हट सकते हैं।

अगर app/admin page ही नहीं खुल रहा हो तो सीधे GitHub Actions और Supabase dashboard खोलें।

Error होने पर क्रम

  1. User से समय, काम का नाम, screenshot और User ID लें। Password, OTP या API key न लें।
  2. API Health के पिछले 24 घंटे के category/code देखें; यह सभी provider logs नहीं है। Server functions और provider logs अलग देखें।
  3. 401: session/key; 403: admin/RLS/activation; 429: quota/rate limit; 500: server error; timeout/network: connection या provider धीमा।
  4. बार-बार paid generation चलाकर परीक्षण न करें। पहले configuration और quota देखें। Payment failure पर bank/provider status की पुष्टि के बिना manual double-credit न दें।
  5. बड़ी समस्या पर App Settings maintenance सूचना Publish करें। यह informative सूचना है; पूरे backend को रोकने वाला switch नहीं है।
  6. Fix → छोटा सुरक्षित test → deploy/tests → desktop और वास्तविक फोन पर verify → maintenance सूचना हटाएँ।

आपके पास नियंत्रण और सुरक्षित access

Supabase organization, GitHub repository, Cashfree merchant, Sarvam/Brevo/Cloudflare और Play Console के owner/admin accounts आपके अपने email पर होने चाहिए। App का admin login provider का owner account नहीं बनाता। Provider ownership बदलने के लिए उसका dashboard उपयोग करें। Supabase Auth password सुरक्षा settings में leaked-password protection की उपलब्धता भी देखें; मौजूदा project में यह बंद है। Recovery email, 2FA codes, app signing key और source/database backups सुरक्षित अलग जगह रखें।

App में रोज़ catalog/settings/users/rates/reminders और renewal records संभाल सकते हैं। नए features और software bugs के लिए source-code बदलाव चाहिए। Admin को arbitrary public JavaScript या server secrets edit कराने वाला असुरक्षित textbox नहीं दिया गया है।

Play Store · अगला अलग चरण

यह अभी website/PWA है; signed Android package/AAB और Play Store listing तैयार नहीं मानी गई है। Chrome का Install App, Play Store installation से अलग है।

  • Android package ID, signed AAB, signing custody, HTTPS domain association/TWA या चुनी हुई native wrapper व्यवस्था।
  • असली Android पर editing, keyboard/phonetic, audio permission, recording/export/download/share, offline/update और login जाँच।
  • Digital membership/AI features के लिए Play Billing नीति; भारत में eligible alternative-billing enrollment की शर्तें अलग हैं। Cashfree website checkout को बिना policy review Android में न जोड़ें।
  • Privacy policy, Data safety, permissions, content rating, account deletion की in-app और web व्यवस्था, store screenshots/description।
  • नए personal developer accounts पर Console के अनुसार closed-testing requirements और production access approval।
